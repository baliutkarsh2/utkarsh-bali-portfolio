The first thing you build when you start testing an AI agent is a single-turn eval.
You write a prompt, you assert something about the response, and it passes. Then you
ship, and the agent does something that makes no sense on the fourth message of a real
conversation.

This is not a model quality problem. It is a test harness problem, and it comes down to
one thing: **your mocks do not remember anything.**

## The shape of the failure

A typical agent test looks like this. A tool gets stubbed to return a fixed payload, the
agent is asked to do something, and the transcript is checked.

```ts
// The mock every agent test starts with, and the reason it passes.
const tools = {
  getOrder: async () => ({ id: "ord_123", status: "shipped" }),
  cancelOrder: async () => ({ ok: true }),
};
```

That harness cannot fail in an interesting way. `getOrder` returns `shipped` forever, so
the agent never has to reconcile a world that changed underneath it. `cancelOrder`
returns `ok` even when cancelling is impossible.

Now make the mock hold state:

```ts {4,9-11}
function createStore() {
  const orders = new Map([["ord_123", { status: "shipped" }]]);
  return {
    getOrder: async (id: string) => orders.get(id) ?? null,
    cancelOrder: async (id: string) => {
      const order = orders.get(id);
      if (!order) return { ok: false, reason: "not_found" };
      // A shipped order cannot be cancelled. The agent has to notice.
      if (order.status === "shipped") return { ok: false, reason: "already_shipped" };
      order.status = "cancelled";
      return { ok: true };
    },
  };
}
```

The test suite that was green a moment ago now finds real problems. Agents will confirm
a cancellation that returned `ok: false`. They will call `getOrder` again and narrate the
stale value they remember instead of the one they just received. They will apologise and
retry the identical call, unchanged, three times.

None of those are exotic. All of them are invisible to a stateless mock.

## Why turn three

Turns one and two are usually fine because the agent is still operating on the prompt.
By turn three it is operating on its own accumulated context, and that context now
contains its earlier claims. If one of those claims was wrong, everything after inherits
it.

> The interesting failures are not the model being wrong. They are the model being
> consistent with something it was wrong about earlier.

That is also why retry logic can make things worse. Retrying a call whose failure was
semantic rather than transient just produces the same failure with more confidence.

## What this changes about testing

Three things worth doing, roughly in order of payoff:

1. **Make mocks stateful before you make them realistic.** A crude in-memory map that
   enforces one real invariant catches more than an elaborate fixture that enforces none.
2. **Assert on the transcript, not the final message.** The failure is usually a tool
   call that should not have happened, and by the last message it has been smoothed over.
3. **Grade semantically.** String matching cannot tell the difference between "I have
   cancelled that" and "I could not cancel that, it already shipped." A rubric can.

I spent a while building exactly this at [Checkpoint](/projects/checkpoint), and the
part I underestimated was the third one. Generating adversarial conversations is not
hard. Deciding what counts as a failure, and making that judgment reproducible across
runs, is where the actual work is.
